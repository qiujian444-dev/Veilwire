# 通话信令规范 v0

> 2026-10-20 · 对应代码 `rust/crates/client/src/call.rs`、`secure::kind`
>
> 范围：语音/视频通话的**信令**。媒体层用 WebRTC，不在本文档范围内。

## 1. 为什么信令也走消息队列

三条备选：

| 方案 | 问题 |
|---|---|
| 单独开一个信令服务 | 多一个必须被发现的服务器，多一份元数据；与"官方不运营公共服务"冲突 |
| 中继上加一个实时通道 | 要改中继协议，且中继能看出"这两个队列在通话" |
| **复用已加密的消息队列** | 中继看到的只是一条普通密文，和聊天消息无法区分 |

选第三条。代价是信令和聊天消息共享队列语义：**可能重复投递、可能乱序、可能延迟**。
这是第 3 节所有设计的原因。

## 2. 信封

信令是 `secure::Payload` 的一个 `kind`，`body` 里放该类型的 JSON：

```json
{
  "v": 1, "id": "<msg-id>", "from": "<ed25519>", "ts": 1700000000,
  "text": "", "kind": "call.offer",
  "body": "{\"call_id\":\"...\",\"sdp\":\"v=0\\r\\n...\",\"video\":false}"
}
```

`kind` 缺省为 `"text"`（`#[serde(default)]`），所以**加这个字段不会破坏旧消息**。

`body` 用 JSON **字符串**而不是嵌套对象：跨 JNI / 跨语言时字符串没有类型歧义
（Kotlin 侧拿到 `optString`，Rust 侧拿到 `String`，不需要两边都对齐数字/布尔的可空语义）。

## 3. 五种信令

| kind | 方向 | body |
|---|---|---|
| `call.offer` | 主叫 → 被叫 | `{call_id, sdp, video, restart}` |
| `call.answer` | 被叫 → 主叫 | `{call_id, sdp}` |
| `call.reject` | 被叫 → 主叫 | `{call_id, reason}` |
| `call.ice` | 双向 | `{call_id, candidate, mid, mline}` |
| `call.end` | 双向 | `{call_id, reason}` |

`call_id` 是发起方生成的 32 位 hex，**全程不变**。

`reason` 取值：`declined` / `busy` / `no_answer` / `missed` / `local_ended` / `peer_ended` / `internal_error` / `no_media`。

`restart`（默认 `false`）表示这是**通话中的重新协商**，见 4.4 节。

## 4. 状态机

```
                start_outgoing
   Idle ──────────────────────────► Outgoing
    │                                  │
    │  on_offer                        │ on_answer
    ▼                                  ▼
 Incoming ──── accept ────────────► Active
    │                                  │
    └── reject ──┐        hangup ──────┤
                 ▼                     ▼
               Ended ◄──── on_end ─────┘
                 │
                 └── reset ──► Idle
```

### 4.1 三条硬性语义

**① 每条信令都必须校验 `call_id`。**

这不是洁癖，是必需。中继在没收到 ACK 时会重投，上一通电话的 `call.end`
完全可能在**下一通电话接通之后**才到。不校验 `call_id` 的结果就是：
新的通话被一条旧信令挂断。有测试 `late_end_from_previous_call_is_ignored` 守着。

**② 忙线时回 `reject(busy)`，绝不抢占。**

抢断会让正在通话的双方都被踢掉。系统里同一时刻只能有一通电话，
第二通来电者收到 busy，当前通话状态完全不受影响。
测试：`busy_rejects_without_disturbing_current_call`。

**③ ICE 不做状态检查，只校验 `call_id`。**

`candidate` 完全可能先于 `answer` 到达主叫端（answer 和 ICE 是两条独立的投递）。
如果因为"当前还是 Outgoing 状态"就把候选丢掉，只能等重传，弱网下常表现为
"接通了但没声音"。测试：`ice_before_answer_is_passed_through`。

App 侧还有一层对应的处理：远端描述没设好之前收到的 candidate 先缓存，
`setRemoteDescription` 成功后统一灌进去（`CallManager.pendingCandidates`）。

### 4.2 超时

- 振铃 45 秒（`RING_TIMEOUT_SECS`）。
- 主叫超时 → 本地 `no_answer`，**发 `call.end` 让对方停止振铃**。
- 被叫超时 → 本地 `missed`，**不发**（对方的计时器会自己超时，多发一条只是噪音）。

### 4.3 去重

同一条 `call.offer` 被中继重投时只能弹一次来电界面。去重键用**中继层的消息 ID**
（`Incoming.msg_id`），保留最近 64 条。

### 4.4 通话中换网络（ICE restart）

WiFi 切到移动网之后，之前收集的候选全部失效。不处理的话表现是
"双方都还在通话界面里，但谁也听不见"——比直接断线更难排查。

做法是把重协商**复用 `call.offer`**，用 `restart: true` 区分：

```
主叫（换网）                          被叫
  createOffer(IceRestart=true)
  ── call.offer{restart:true} ──►    状态仍 Active，不弹界面
                                       setRemoteDescription(offer)
                                       createAnswer
  ◄──── call.answer ───────────      状态仍 Active
  setRemoteDescription(answer)
```

四条必须守住的规则：

1. **`restart` 的 offer 必须在"忙线拒接"之前判断。** 否则对端正在说话的通话会被当成新来电挂掉。
2. **只有 `Active` 才接受重协商。** 还没接通就重协商没有意义，会把状态机从 `Incoming` 直接推到 `Active`。
3. **`call_id` 仍要校验。** 上一通电话的重协商迟到，不能影响当前这通。
4. **重协商不改通话计时。** 第一次接通才记 `connectedAt`，否则每换一次网通话时长就归零。

触发方式两条并行：

- **自动**：`ConnectivityManager.registerDefaultNetworkCallback` 检测到默认网络变化，等 1.5 秒稳定后发起。
- **手动**：通话界面的"重连"按钮。自动检测不一定每次都准（比如同一网络下 NAT 映射过期但网络没变），
  留个人工兜底比让用户干等好。

## 5. 消息大小

| 字段 | 上限 | 理由 |
|---|---|---|
| `sdp` | 8 KiB | 正常 offer 2~4KB，8KB 已经很宽松 |
| `candidate` | 1 KiB | 单个候选通常 < 200 字节 |
| `call_id` | 64 字符 | 实际用 32 |

超出上限的信令**直接丢弃**，不报错。理由：信令是可重传的，而异常大的载荷
更像是攻击或实现错误，不值得为它改变状态。

## 6. ICE 服务器

信令里**不带** ICE 服务器配置，双方各自按本地设置连自己的 STUN/TURN。

原因：如果让发起方指定 TURN，等于让对端信任一个陌生人给的服务器，
流量会被引到对方控制的机器上。

默认只配一个国内可达的 STUN，TURN 由用户/社区自建（见 `中继部署指南.md`）。

## 7. 已知限制

| 限制 | 影响 | 计划 |
|---|---|---|
| 无 TURN 时跨运营商大概率连不通 | 只能通话同一局域网/同运营商 | P2 接 TURN 配置 UI |
| ~~不支持通话中切换网络后的重协商~~ | ~~从 WiFi 切到流量会断~~ | ✅ 已实现（4.4 节），自动 + 手动两条路径 |
| 不支持多人通话 | 只能 1v1 | 明确不做（与匿名性/复杂度冲突） |
| 群聊的呼叫未定义 | — | 群聊本身还没做 |
| 视频只有 640×480 | 画质一般 | P3 按网络状况自适应 |
| 没有通话记录 | 只有当前这一通 | P1 落库 |
| 状态机只在内存里 | 进程重启后当前通话状态丢失（通话本身也会断） | 可接受；不打算持久化 |
| CLI 的 `calloffer` / `callrecv` 是两个进程 | 两边的状态机互不相通，所以 `callrecv` 里看到的 `state` 会是 `idle` | 仅影响调试工具；看 `kind` 和 `from` 就够判读 |

**信令层（`cli calldemo`，真实中继 + 真实加密）**

```
=== 2. Alice 发起通话 ===   call_id = 61f67e04...
=== 3. Bob 收到 offer ===   kind=call.offer state=incoming video=false
=== 4. Bob 接听 ===         Bob 本地状态 = active
=== 5. Alice 收到 answer === Alice 本地状态 = active
=== 6. 双向 ICE 交换 ===    Bob 收到候选 / Alice 收到反向候选
=== 7. 忙线保护 ===         来电 → Bob 状态仍是 active；Carol 收到 call.reject reason=busy
```

## 8. 实现位置

| 层 | 位置 | 职责 |
|---|---|---|
| 状态机 | `rust/crates/client/src/call.rs` | 全部状态迁移、校验、超时、重协商。22 个单元测试 |
| 粘合 | `rust/crates/client/src/lib.rs` (`call_*`) | 把 `Action` 执行成真实发送 |
| JNI | `rust/crates/android-jni/src/lib.rs` | 10 个导出函数 |
| 媒体 | `android/.../CallManager.kt` | PeerConnection、采集、渲染 |
| 界面 | `android/.../CallScreen.kt` | 振铃/通话/结束三种形态 |

**信令的编码与发送全在 Rust 侧**，Kotlin 不接触密钥、不拼信令 JSON。
这样 CLI 和 Android 走的是同一份实现，且状态机可以被单元测试穷举。
