# 去中心化匿名聊天软件 — 可行性方案与技术规划

> 版本 **v0.4（决策定稿）** · 2026-10-20
> 目标平台：**Android（一期仅手机端）**
> 产品定位：**开源软件，官方不运营任何公共服务，中继由用户/社区自建，官方只发代码和部署文档**
> 市场：面向海外及中国港澳台地区、华人群体；境内仅 APK 直装，不上架国内应用商店
> 许可证：**AGPL-3.0-only**（仅第 3 版，不含 or-later）
>
> **v0.4 变更（本版）**：D1~D5 全部定稿，不再有开放决策。协议层选定 **SimpleX 风格队列模型自研**，核心层 **Rust**，恢复短语 **BIP39 12 词**，中继列表 **官方仓库收录 + 免责声明**，**预留 `PushProvider` 空接口 / 默认关闭 FCM**。开发进入阶段 0。
> **v0.3 变更**：砍厂商推送，改为电池白名单 + 前台服务长连接；合规定位与分发策略定稿；新增中继生态设计。
> **v0.2 变更**：砍 Windows，UI 从 Flutter 改为 Kotlin + Compose，核心层保留 Rust。

## 0. 一句话结论

**可行，但必须先纠正一个前提：Session 那种"纯去中心化网络"在国内走不通，我们只能做"无中心账号 + 可自托管中继"的架构。**

**「无中心」不等于「无服务器」。** Session 自己也有 1500+ 台服务节点在跑，它只是没有一家公司说了算。我们真正要的——不依赖单一服务器、没有账号体系、节点可被任何人替代——可以做到；而"数据包只在两台设备之间流动、全程不经过任何第三方机器"在国内做不到，因为离线消息和音视频都需要中继兜底。

**砍掉推送的决定是对的，但理由要换**：不是因为"申请麻烦"，而是因为**推送服务商必然知道"这台设备在某时刻收到了一条消息"——这与匿名定位根本冲突**。SimpleX、Session、Briar 都不接推送服务，理由相同。

代价是：**必须让用户授予电池优化白名单**，否则消息延迟会到几十分钟级。这是本方案最重要的一条产品约束，第 6 节详述。

| 需求 | 判定 | 说明 |
|---|---|---|
| 1v1 文本聊天 | ✅ 可行 | 中继 + 端到端加密，443/TLS 放行 |
| 图片 / 文件传输 | ✅ 可行 | 直连优先，中继兜底；≤64MB |

## 2. 为什么 Session 的模式在国内走不通

```
客户端 A → [Node1] → [Node2] → [Node3] → 目标 Swarm(5~7 台存储节点) → 客户端 B
           洋葱路由 3 跳（TCP），消息在 swarm 加密存储，默认保留 2 周
```

1. **节点列表是硬编码 IP。** 启动时先连 seed node 拿列表，列表里是每台节点的公网 IP + 端口 + 公钥。封掉这些 IP，整个网络就断了——**俄罗斯就是这么干的**。Session 团队在 FLOSS Weekly 播客里确认：俄罗斯已完全封锁其网络；中国区 App Store 已下架，只能侧载。
2. **入口是境外 IP。** 1500+ 节点分布在 50+ 国家，境内基本没有节点（运营需备案 + 涉币质押）。第一步握手就出境。
3. **TCP 非标端口，无伪装。** 对 DPI 来说是典型可疑流量。
4. **音视频不是它强项。** 官方文档自己写：Onion Requests 是"很有限的、基于 TCP 的消息协议"，不适合大文件和实时音视频。

**结论：照抄 Session = 造一个在国内连不上的软件。**

## 3. 国内网络现实

| 事实 | 数据 | 影响 |
|---|---|---|
| IPv6 覆盖率极高 | 活跃用户 8.69 亿（77.38%），**移动网 IPv6 流量占比 70.85%**，家庭网关 IPv6 开启率 98.41% | 手机↔手机 P2P 直连有戏（本期只做 Android，正好吃满） |
| 国际出口 IPv6 流量占比极低 | 9.13% | 境外节点基本不可用，中继必须在境内 |
| WebRTC 不被封 | 腾讯会议/钉钉/微信均基于它 | 音视频走 WebRTC 安全 |
| 移动网上行 UDP 被 QoS | 普遍现象 | 视频通话必须准备 TURN over TCP 443 兜底 |
| 运营商 CGNAT 普及 | 4G/5G 广泛 | IPv4 打洞成功率低，**IPv6 是主力** |
| Tor 在国内被封 | 日活约 5000，50% 靠网桥 | 不选 Tor / I2P / onion 系 |

**三条硬约束**：① 用户要连的节点必须在境内；② 协议要像 HTTPS（443/TLS）；③ 不能有唯一入口。

## 4. 三个候选架构

### 方案 A：Nostr 中继 + 自研 E2EE + WebRTC
中继是几百行 WebSocket 服务，wss://443，人人可部署。实现最简单，1~2 人月能跑通 MVP。缺点是原生为公开时间线模型，私聊是补丁，元数据保护弱。国内可用性 ★★★★☆

### 方案 B：SimpleX 队列模型
纯 TLS 443，**无用户 ID、无账户**，消息进随机队列，用完即删。匿名性天花板最高，经 Trail of Bits 审计。缺点是要自己写客户端，Haskell 服务端不好二次开发。国内可用性 ★★★★★

### 方案 C：Session 式洋葱网络
需要激励层维持节点规模；节点 IP 上名单就全灭；国内必然不可用；工作量是前两案 5~10 倍。**一期不做。**

### ✅ 推荐：B 的协议思想 + A 的部署模型 + WebRTC 媒体层

用 SimpleX 的"无标识队列"做消息层（自研 Rust 实现，不 fork Haskell），用"任意人可部署中继"做部署模型，用 WebRTC 做媒体层。

> 这个组合还有一个与"官方不运营"完全契合的性质：**中继是无状态的、可互换的，官方消失后网络照样运转**。如果选用 Matrix 这类有 homeserver 的方案，"官方不运营"会导致新用户根本没有入口。

## 5. 架构详解

### 5.1 分层

```
┌──────────────────────────────────────────────┐
│  Android App                                  │
│  ├ UI 层        Jetpack Compose               │
│  ├ 系统集成层   前台服务 / 权限 / 通知 / 白名单  │
│  └ 业务层       ViewModel + 状态机             │
└───────────────────┬──────────────────────────┘
                    │ UniFFI 生成的 Kotlin 绑定
┌───────────────────▼──────────────────────────┐
│  Core（Rust，未来可被 Windows 端复用）         │
│  crypto · protocol · storage · net            │
└───────────────────┬──────────────────────────┘
                    │
     ┌──────────────┼──────────────┐
     │              │              │
┌────▼─────┐  ┌─────▼──────┐  ┌────▼───────┐
│ P2P 直连  │  │  消息中继   │  │ STUN/TURN  │
│ IPv6/UDP │  │  WSS 443   │  │  coturn    │
└──────────┘  └────────────┘  └────────────┘
 音视频/大文件   文本/信令/离线     通话兜底
```

### 5.2 消息流

```
发送：B 的 X25519 公钥 → 双棘轮派生消息密钥 → 加密 + Ed25519 签名
     → 从邀请信息取 3 个队列地址 → 并发 PUT 到 3 个中继（各带随机 ID）
     → 收到 2/3 个 2xx 即视为投递成功

接收：维持到 3 个中继的 WSS 长连接 → 收密文 → 解密 → 幂等去重 → 落库 → 回 ACK
```

中继只看到：随机队列 ID、密文长度、时间。**看不到身份，看不到社交图谱，没有用户表**。队列 30 天 TTL，投递后即删。

### 5.3 通话流

```
1. 呼叫方生成 offer → 经消息队列加密发给对方（不依赖长连接）
2. 双方并行收集候选：host(IPv6 优先) → 境内 STUN → 同时发包打洞
3. ICE 连通 → DTLS-SRTP 端到端加密媒体流直连
4. 打洞失败（预计 20~30%）→ 回落 TURN（UDP 优先，失败转 TCP/443）
5. 振铃/挂断/忙线信令全部走消息队列
```

**TURN 只转发不解密**，媒体流本身是 DTLS-SRTP 加密的。

预期：同运营商手机↔手机直连率 ≥85%；跨运营商 60~75%，回落 TURN 后延迟 80~150ms。

### 5.4 文件传输

| 大小 | 路径 |
|---|---|
| <1MB | 走消息队列，分片载荷 |
| 1MB~64MB | WebRTC DataChannel 直传 |
| 更大 / 对方离线 | 中继对象存储分片（**P4 之后**） |

大文件传输挂 `dataSync` 前台服务（有明确起止，不是常驻长连接，允许用），但要注意 Android 15 的 6 小时上限，超长传输必须支持断点续传。

### 5.5 身份与加密

| 项 | 方案 |
|---|---|
| 身份 | Ed25519 密钥对，公钥即 ID（Base58，约 44 字符） |
| 加好友 | 二维码 / 一次性邀请链接（含身份公钥 + 队列地址 + 中继列表） |
| 密钥协商 | X3DH（后续 PQXDH 抗量子） |
| 会话加密 | Double Ratchet |
| 本地存储 | SQLCipher，密钥锁在 Android Keystore（硬件级，即使 root 也难提取） |
| 媒体加密 | DTLS-SRTP |
| 设备丢失 | 无云端恢复 → BIP39 恢复短语 |

**取舍**：无手机号/邮箱是匿名性根基，代价是**没有"找回账号"**。必须写进用户协议。

| 层 | 选型 | 备注 |
|---|---|---|
| 语言 / UI | Kotlin + Jetpack Compose | 单端后 Flutter 优势消失 |
| 架构 | MVVM + Coroutines/Flow | |

## 6. 消息触达机制（本版核心，务必读）

### 6.1 先说结论："后台轮询"在 Android 上不成立

这是本版必须纠正的技术认知。官方文档说得很清楚：

> Doze 模式下系统**暂停所有应用的网络访问**（Suspends network access），**不为前台服务提供豁免**。唯一被文档化的豁免途径是电池优化白名单。
> —— [Optimize for Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)

三种"不接推送"的实现方式，实测预期如下：

| 实现方式 | Doze 下的真实表现 | 能不能当 IM 用 |
|---|---|---|
| `AlarmManager` 周期轮询（普通） | 闹钟被推迟到维护窗口，**维护窗口间隔会逐步拉长，最长约 6 小时** | ❌ |
| `setExactAndAllowWhileIdle` 轮询 | Doze 下每 app **最多 9 分钟一次**（低功耗状态可能更慢），且每次都要重连 TLS | ❌ 耗电且延迟 9 分钟起 |
| `WorkManager` 周期任务 | 内部就是 JobScheduler，Doze 下**完全不运行**；App Standby 的 Rare bucket 下**每天约 1 次** | ❌ |
| **前台服务 + 长连接 + 电池白名单** | 白名单后可在 Doze 期间使用网络并持有 partial wake lock | ✅ **唯一可行** |

**所以正确形态不是"轮询"，而是"常驻长连接 + 白名单 + 断线退避重连"。**

### 6.2 推荐实现：三层保险

```
第一层：前台服务（remoteMessaging 类型）+ WSS 长连接常驻
        └─ 断线时指数退避重连（1s → 2s → 4s … 上限 60s），不是定时轮询
        └─ 心跳 30s，3 次无响应判死，立即重连

第二层：电池优化白名单（必须用户手动授予）
        └─ 这是长连接能在 Doze 下存活的前提，没有它第一层会在息屏后失效
        └─ Onboarding 中引导，并检测授予状态；未授予时在 UI 上明确提示"可能延迟收消息"

第三层：AlarmManager 保险丝（兜底，不是主路径）
        └─ setExactAndAllowWhileIdle 每 15 分钟一次，只做一件事：检查连接是否活着，死了就拉起
        └─ 用 JobScheduler/WorkManager 做每日一次的"深度兜底"（设备重启后等场景）
```

### 6.3 必须诚实面对的产品后果

- **没有推送 = App 被系统杀掉期间收不到任何消息**，直到用户打开 App 或保险丝唤醒为止。
- 用户拒绝授予电池白名单 → 息屏后消息延迟可能到几十分钟甚至几小时。
- 所以：**白名单授权不能做成"可选设置"，必须做成 onboarding 的强制步骤**，并且用大白话解释为什么（"不开这个，你锁屏后就收不到消息"）。
- UI 上要显示"上次同步时间 / 连接状态"，**不要假装实时**。这是诚信设计，也能减少用户投诉。

### 6.4 为什么不接 FCM

FCM 免费、不需要企业资质、五分钟就能建项目——技术上确实能解决海外体验。但**它和匿名定位根本冲突**：

- 接 FCM = 每台设备向 Google 注册一个 token，Google 知道"这台设备此刻收到了一条消息"；
- 这正好是我们用无标识队列拼命想消除的那部分元数据；
- SimpleX、Session、Briar 全部拒绝推送服务，理由相同。

**建议一期不接**。架构上留一个 `PushProvider` 接口（空实现），将来若海外用户对延迟抱怨严重，可以作为**默认关闭的可选项**加入，让用户自己在"实时性"和"元数据"之间选。

> 顺带一提：砍掉五家国产厂商推送，除了麻烦，还省掉了"推送体过厂商服务器"和"需要企业资质"两个问题。这个决定在匿名性上是自洽的，只是实现方式要从"轮询"改成"长连接"。

## 7. Android 平台专项

### 7.1 前台服务类型：选错就等于没有后台

| 类型 | 能否用于 IM 长连接 | 说明 |
|---|---|---|
| `remoteMessaging` | ✅ **首选** | Android 14 新增，专为跨设备传递消息设计，**无运行时长限制** |
| `dataSync` | ❌ **禁用（长连接场景）** | Android 15 起 24h 内累计只能跑 6 小时，超时抛 `RemoteServiceException` 崩溃。**仅用于文件传输** |
| `phoneCall` | 通话时用 | 配 `CallStyle` 通知 |
| `microphone` / `camera` | 通话时叠加 | 必须先拿运行时权限**再** `startForeground()`，顺序反了直接 `SecurityException` |
| `specialUse` | 兜底 | 需 Play 审核说明，非必要不用 |

```xml
<service
    android:name=".service.MessagingService"
    android:foregroundServiceType="remoteMessaging"
    android:exported="false" />
```

需配 `FOREGROUND_SERVICE_REMOTE_MESSAGING` 权限。通话时用 `ServiceCompat.startForeground()` 传 `remoteMessaging|phoneCall|microphone|camera` 位掩码。

### 7.2 硬坑清单

| # | 坑 | 对策 |
|---|---|---|
| 1 | `POST_NOTIFICATIONS`（API 33+）被拒 → 前台服务通知不显示 | 首启引导；拒绝后降级为"仅前台收消息"并明确告知 |
| 2 | Android 14 起禁止从后台启动前台服务 | 高优先级闹钟、`BOOT_COMPLETED`、用户点击；`remoteMessaging` 不受 Android 15 的 `BOOT_COMPLETED` 限制 |
| 3 | **Doze 掐断网络（前台服务也不豁免）** | **电池优化白名单**——本方案的前提条件，见 6.2 |
| 4 | 国产 ROM 二次限制（MIUI/EMUI/ColorOS/MagicOS/Flyme） | 除 AOSP 白名单外，还需引导用户在厂商的"自启动 / 受保护应用 / 后台运行"里单独开启，做成一键跳转引导页 |
| 5 | 被用户"强行停止"后无法自动拉起 | 只能提示用户重新打开；UI 上要有明确的状态提示 |
| 6 | 通话时息屏 / 切后台 | `phoneCall` 前台服务 + `PROXIMITY_SCREEN_OFF_WAKE_LOCK` + 音频焦点 |
| 7 | 蓝牙耳机 / 免提切换 | `AudioManager.MODE_IN_COMMUNICATION` + 路由管理，通话体验的分水岭 |
| 8 | Google Play 政策：禁止随意申请 Doze 豁免 | 需在商店listing 中声明"核心功能受影响"，准备申报文案（IM 属合理用途） |
| 9 | APK 分发 | 境外商店 + 官网 APK + F-Droid 自建仓库；**不上架国内商店** |

## 8. 定位、合规与分发（已定稿）

### 8.1 定位（本版确认）

| 项 | 决定 |
|---|---|
| 项目性质 | **开源软件**（AGPL-3.0-only） |
| 官方角色 | **不运营任何公共服务**：不跑境内中继、不跑 TURN、不做账号服务、不做推送 |
| 官方交付物 | 客户端代码 + 中继/部署文档 + 一键部署脚本 |
| 基础设施 | 由用户、社区、第三方自建 |
| 市场 | 海外及中国港澳台地区、华人群体 |
| 境内分发 | 仅 APK 直装（官网 / GitHub Releases），**不申请国内应用商店、不做境内推广** |

### 8.2 这个定位解决了什么，没解决什么

**解决**：绕开了 ICP 备案、APP 备案、软著、应用商店审核、实名制落地要求——因为我们不是"境内运营的即时通讯服务提供者"。

**没解决**：
- 境内用户自建中继仍需自行承担当地监管责任（软件许可协议里要写清）；
- "境内可用"从此变成**社区能力的函数**，官方不再承诺 SLA；
- 代码托管、官网、下载页全部放在境外，避免境内主体暴露。

### 8.3 境内可用性责任的转移

这是本版最重要的定位后果：

> **官方不再提供"国内可直连的默认中继"。国内能不能用，取决于社区有没有人在境内跑中继。**

所以产品设计上必须解决"新用户装完 App 之后连哪里"的问题——见第 9 节。这一节不做，App 装完就是一块砖。

## 9. 中继生态与首次启动（P0 必做）

官方不运营中继，导致一个绕不过去的体验问题：**首次启动时，客户端不知道连谁。**

### 9.1 三级中继来源

```
① 引导层（Bootstrap）：一个极轻量的静态分发
   └─ 托管在境外（GitHub Pages / 对象存储），只放 JSON：社区中继列表 + 签名
   └─ 客户端首次启动拉取，之后本地缓存，可离线使用

② 社区层：社区 PR 维护的中继列表
   └─ 官方仓库收录，但明确声明"不背书、不运维、不保证可用"
   └─ 每条记录带：URL、地区、运营者声明、自测时间
   └─ 客户端内置"一键测速 / 可用性检测"，让用户自己选

③ 自定义层：扫码 / 粘贴 URL 添加
   └─ 自己家软路由、NAS、云主机都能当中继
   └─ 这是"去中心化"最硬核的入口，必须做好
```

### 9.2 首次启动流程（建议）

```
启动 → 生成身份密钥对（无需注册，无感知）
     → 展示恢复短语（要求用户确认抄写）
     → "选择中继"页：
         · 自动拉取列表并按延迟排序
         · 显示每个中继的地区和存活状态
         · 默认勾选 3 个延迟最低且地区不同的
         · 底部有"我有自己的中继 → 扫码/输入"
     → 电池白名单引导（强制步骤，解释清楚为什么）
     → 进入主界面
```

**这一步做不好，前面所有技术都白费。** 建议按"给非技术用户看也能懂"的标准做文案。

### 9.3 中继运营者的门槛

官方交付的部署物必须做到"一条命令起服务"：

```bash
docker run -d --name relay -p 443:443 \
  -v ./data:/data -v ./certs:/certs \
  ghcr.io/<org>/relay:latest
```

配套文档要覆盖：域名解析、证书自动签发（ACME）、境内服务器的注意事项、带宽估算（1 万用户约需多少）、被封 IP 后怎么换。

## 10. 关键风险与对策

### 🔴 R1：无推送模式下的消息延迟（最高优先级）

见第 6 节。核心对策：`remoteMessaging` 前台服务 + 电池白名单强制引导 + 三层保险。

**这条决定产品能不能"当日常 IM 用"，必须在阶段 0 实测，不能留到 P0 末尾。**

### 🟠 R2：用户不给白名单

国产 ROM 用户对"电池优化白名单"普遍警惕（也可能被安全软件拦截）。

对策：onboarding 做成"三步图文 + 一键跳转 + 实时检测"，并给出对比演示（授权前/后的收消息延迟）。不给就降级并明确告知，不骗用户。

### 🟠 R3：NAT 穿透不达预期

阶段 0 实测。按 30% 流量走 TURN 规划带宽。可引入"用户互助中继"（有公网 IPv6 的用户一键开中继）摊薄成本。

### 🟠 R4：社区中继不足以支撑规模

官方不运营 = 早期很可能只有几台社区中继，性能和可用性都不可控。

对策：客户端必须支持**多中继冗余 + 自动故障转移**；引导层列表要能快速更新；文档里给出"自建中继"的最低成本方案（一台 1C1G 的 VPS 或家里的旧设备）。

### 🟡 R5：中继被批量封 IP

对策：客户端支持自定义中继列表；中继部署脚本支持一键换 IP；文档教运营者用 CDN/域名前置等常规手段（注意：这可能带来合规争议，文档只做技术说明）。

### 🟡 R6：GPLv3 传染

`libsession` / `session-android` / `session-desktop` 均为 GPLv3。**只能读架构，不能抄代码**。建议项目本身用 AGPLv3。

## 11. 开发排期

### 阶段 0：可行性验证（1~2 周）— go/no-go 关卡

| 0.4 | WebRTC 音视频 | libwebrtc demo + 自建 coturn，实测 30 通 | 接通率 ≥95%，MOS ≥3.5 |
| 0.4a | ~~媒体栈可用性~~ | ✅ 已完成：单机双 PeerConnection 自检（`--ez selftest true`） | ICE_CONNECTED，PASS |

## 附：不采用的方案速查

| 方案 | 否决原因 |
|---|---|
| Tor / OnionShare | 国内全面封锁，需网桥，延迟 1~3s |
| Tox | DHT 无离线消息；UDP 被 QoS；bootstrap 在境外 |
| Briar | 基于 Tor |
| I2P | 生态弱，国内不可用 |
| Jami | DHT + SIP，UDP 穿透差 |
| Matrix | 有 homeserver 中心节点；与"官方不运营"定位冲突（新用户无入口） |
| ZeroTier / Tailscale | 依赖协调服务器，国内不稳定 |
| Bitchat（BLE Mesh） | 只适合近距离离线 |
| **FCM / 五家国产厂商推送** | 推送服务商必然获知"设备有消息"，与匿名定位冲突；国产厂商还需企业资质 |
| **AlarmManager / WorkManager 轮询** | Doze 下 9 分钟起、维护窗口可拉长到 6 小时；WorkManager 在 Doze 下根本不跑 |
