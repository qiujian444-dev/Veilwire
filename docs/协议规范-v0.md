# 协议规范 v0（草案）

> 状态：阶段 0 草案，随实现同步演进
> 对应代码：`rust/crates/{proto,relay,identity,cli}`
> 读者：想实现第二个客户端的人（包括未来的我们自己）

## 0. 设计约束（先看这个，否则后面很多决定看着莫名其妙）

| 约束 | 由此产生的设计 |
|---|---|
| 国内不开 VPN 可用 | 传输必须是标准 TLS + WebSocket(443)；端点必须在境内 |
| 官方不运营服务器 | 协议不能假设"有一个默认服务器"；中继地址必须可配置、可替换、可多个 |
| 匿名 | 中继不能有用户表；不存身份、不存社交关系；队列 ID 与身份无关 |
| 无推送 | 客户端必须能长期持有连接；协议要支持廉价心跳和快速重连补齐 |
| 弱网 + 会断 | 所有消息必须幂等（可安全重发）；离线补齐是一等公民 |

## 1. 术语

| 词 | 含义 |
|---|---|
| 身份（Identity） | 一对 Ed25519 密钥。公钥的 base64url 就是 ID，43 字符 |
| 队列（Queue） | 中继上的一个匿名信箱，用 32 位十六进制 ID 标识。**由接收方创建** |
| 中继（Relay） | 存转队列消息的服务器，可被任何人部署，无状态（除队列本身） |
| 邀请（Invite） | 接收方生成的一次性字符串/二维码，含接收方身份公钥 + 队列 ID + 中继地址 |
| 信封（Envelope） | 投递到队列里的那层结构：路由信息（明文，给中继看）+ 密文（给接收方看） |

## 2. 身份与邀请

### 2.1 身份

- 算法：Ed25519（签名）；X25519 由同一密钥材料派生，用于密钥协商
- ID：`base64url_nopad(ed25519_public_key)` → 43 字符
- **没有注册流程**。生成密钥即拥有身份。
- 恢复：32 字节种子 → BIP39 12 词（P0 实现）

### 2.2 邀请码

```
anonchat://invite/<base64url_nopad(JSON)>
```

JSON：

```json
{
  "v": 1,
  "pk": "<接收方身份公钥 base64url>",
  "qid": "<接收方队列 ID，32 位 hex>",
  "relays": ["wss://relay.example.com", "wss://relay2.example.com"],
  "name": "阿甲"
}
```

规则：

- `v` 不匹配 → **必须拒绝**，不能"尽力解析"。字段语义会随版本变化。
- `relays` 必须 1~8 个，scheme 只能是 `ws://`（调试）或 `wss://`（生产）。
- `name` 纯展示，不参与任何认证——**不要用它做身份判断**。
- 邀请码由接收方生成，因此"加好友"这个动作在网络上不留痕迹：
  发送方只是知道了往哪个队列投，中继不知道这两人建立了关系。

### 3.x 队列的生命周期（容易踩的坑）

队列**只能由中继分配**（`new_queue`），而最初只有"生成邀请码"这条路径会去申请。
后果：一个只"加了别人"、自己没出过码的设备根本没有收件地址——它的消息发得出去，
却收不到任何回复，界面上看起来完全正常。

所以客户端必须在拿到中继地址后补建队列（`client::ensure_queue`）：
引导完成、加好友成功、服务每次启动各补一次，已有则只补充中继列表。
这条规则是新设备能不能被回复的前提，不是可选项。

> 已知弱点：邀请码**不带签名**，信任模型是 TOFU。
> 已补一半：v0.6.0 起有**双人安全码比对**（见 4.6.1），可以带外发现身份被替换；
> 邀请码本身的签名还没做。

## 3. 中继协议

### 3.1 传输

WebSocket over TLS，路径任意（建议 `/`），单连接多路复用多个队列。

生产部署由 Caddy/nginx 终止 TLS，中继只监听 `127.0.0.1`。这样对外就是一个普通 HTTPS 站点。

### 3.2 帧格式

阶段 0 用 JSON 文本帧。P0 切 CBOR（体积和解析开销都更小）。

**客户端 → 中继**

| `t` | 字段 | 语义 |
|---|---|---|
| `new` | `v` | 创建队列。版本不符返回 `bad_version` |
| `sub` | `qid` | 订阅：此后该队列的新消息主动推送；同时补投积压 |
| `put` | `qid`,`id`,`body` | 投递。`id` 是客户端生成的消息 UUID，用于幂等 |
| `get` | `qid` | 拉取全部未确认消息（重连补齐用） |
| `ack` | `qid`,`ids` | 确认消费，中继删除这些消息 |
| `ping` | — | 心跳 |

**中继 → 客户端**

| `t` | 字段 | 语义 |
|---|---|---|
| `new_ok` | `qid`,`ttl` | 队列创建成功，`ttl` 为秒 |
| `ok` | `ref_id` | 操作成功 |
| `msg` | `qid`,`id`,`body`,`ts` | 推送/拉取到一条消息 |
| `pong` | — | 心跳响应 |
| `err` | `code`,`msg` | 错误 |

### 3.3 错误码

| code | 触发条件 | 客户端应做什么 |
|---|---|---|
| `bad_version` | `new` 的 `v` 不匹配 | 提示升级，不要重试 |
| `bad_json` | 帧不是合法 JSON | 修 bug |
| `bad_frame` | 非文本帧 | 修 bug |
| `no_queue` | 队列不存在或已过期 | 重新建队列 + 重新分发邀请 |
| `too_large` | `body` 超过 64 KiB | 走文件通道 |
| `rate_limited` | 超过每连接投递速率（默认 120 条/分钟） | 退避重试，不要立即重发 |

### 3.4 状态机

```
        new ──> [队列已创建] ──> sub ──> [订阅中]
                                  │         │
                                  │         ├─ 收到 msg ──> ack
                                  │         │
                                  └─────────┴─ 断线 ──> 重连 ──> sub / get
```

### 3.5 三条必须遵守的语义

1. **幂等**：同一个 `id` 重复 `put`，中继既不能重复入队，**也不能重复推送**。
   否则对端重放同一个 ID 就能无限轰炸接收方。
2. **先存后推**：`put` 必须先落队列，再通知订阅者。反过来会在推送成功但存盘失败时丢消息。
3. **ACK 才删**：不 ACK 就保留到 TTL 过期。这是"离线补得回来"的基础。
4. **订阅先回 OK，再补投积压**。顺序不能反：如果积压不为空就跳过 OK 直接推 `msg`，
   客户端在等订阅确认时会把第一条消息当成确认帧吞掉，那条消息就永久丢了。
   （这个 bug 实际出现过，靠端到端测试才发现）

### 3.6 生命周期

- 队列 TTL：30 天（`QUEUE_TTL_SECS`）。每次 `put` 是否续期：阶段 0 不续期，P0 改为"有活动则续期"。
- 消息体上限：64 KiB（阶段 0）。大文件走 WebRTC DataChannel。
- 订阅者列表是**内存态**，连接断开必须清理，否则内存泄漏。
- 速率限制：每连接 120 条/分钟（`--rate` 可调），超出返回 `rate_limited`。
  没有它，一个脚本就能把中继磁盘写满。

### 3.7 持久化

中继把三种事件追加到 `queues.log`（一行一条 JSON）：

```
{"op":"new","qid":"...","exp":1700000000}
{"op":"put","qid":"...","id":"...","body":"<base64>","ts":1700000000}
{"op":"ack","qid":"...","ids":["..."]}
```

- **启动重放**：按顺序应用，重建内存状态，然后清一次过期队列。
- **崩溃容忍**：单行损坏跳过并计数，不阻断启动（否则一次掉电就永久起不来）。
- **压缩**：追加量超过有效数据阈值时，重写到临时文件再原子 rename。
- **默认不 fsync**：崩溃最多丢最后几秒写入；客户端没收到 ACK 会重发。
  `--fsync` 可开启，吞吐降一个数量级。

## 4. 端到端加密层

已实现，代码在 `rust/crates/secure`。用的是 **Olm**（Matrix 的双棘轮实现，`vodozemac` 0.9）。

> 为什么不自研双棘轮：密码学实现出错是静默的、灾难性的。vodozemac 是纯 Rust、独立审计过，
> API 面比 libsignal 小一个量级，对一期足够。

### 4.1 密钥分层

| 密钥 | 算法 | 用途 | 是否对外 |
|---|---|---|---|
| 身份密钥 | Ed25519 | 对外 ID、人类可读身份 | 公钥公开 |
| 身份 DH 密钥 | X25519 | 3DH 的第一把 | 公钥放进邀请码 |
| 一次性预共享密钥（OTK） | X25519 | 3DH 的第二把，**用一次即作废** | 公钥放进邀请码 |
| 会话密钥 | 双棘轮派生 | 每条消息独立 | 永不离开设备 |

**为什么邀请码要带 OTK**：我们没有中心服务器来分发预共享密钥池，只能把它塞进邀请码。
代价是**一个邀请码只能用一次**——第二个人拿同一个码建立会话会失败。这是无中心分发的固有成本，
必须在产品文案里说清楚（"这个二维码只给对方扫一次"）。

### 4.2 会话索引

会话按**对方 X25519 身份 DH 公钥**（base64）索引，不按 Ed25519 ID。
原因很实际：收到首条预共享消息时，能拿到的只有对方的 DH 公钥，拿不到 Ed25519 ID。
Ed25519 ID 只用于展示（载荷里的 `from` 字段）和联系人建档。

### 4.3 信封（中继能看到的全部内容）

```json
{ "mt": 0, "ct": "<base64 密文>" }
```

- `mt`：0 = 预共享（首条），1 = 普通
- 中继只能看到这两个字段。它不知道发送方、不知道内容、也推不出会话关系。

### 4.4 载荷（加密之后的明文结构）

```json
{
  "v": 1,
  "id": "<消息 UUID，用于去重>",
  "from": "<发送方 Ed25519 ID>",
  "ts": 1700000000,
  "text": "你好",
  "reply_qid": "<发送方队列 ID，可选>",
  "reply_relays": ["<发送方在用的中继>"],
  "self_name": "<发送方自报的显示名>",
  "kind": "text",
  "body": "<控制类消息的结构化内容，JSON 文本>"
}
```

`reply_qid` / `reply_relays` / `self_name` 三个字段合起来就是**回信线索**（"回邀"用），
缺一不可：队列决定投给谁、中继决定从哪投、名字决定界面上怎么称呼。
接收方会把"投递这条消息的中继"排在 `reply_relays` 最前面——它一定可达，
对方自报的中继只是候选。

信任边界（重要）：这三个字段都是**自报**的，只有 `dh` 是加密层确认过的。
所以接收方只允许把"已有 Olm 会话的 dh"加进通讯录（`Device::has_session` 是那道闸），
名字/队列/中继只当路由线索：猜错了最坏是投不出去，不可能把消息发给别人
（加密目标由 `dh` 决定，不由这些字段决定）。

### 4.4.1 应用层 `kind` 的约定

`kind` 决定接收方怎么处理载荷。目前有三种：

| kind | 含义 | 是否进聊天记录 |
|---|---|---|
| `text` | 普通聊天消息 | 是 |
| `call.*`（`call.offer` / `call.answer` / `call.ice` / `call.hangup` …） | WebRTC 信令，见《通话信令-v0》 | 否（否则聊天记录里会出现一堆空白气泡） |
| `file` | 文件分块 | 只有收齐的那一条进记录 |

**`file` 的块格式**（`body` 是一个 JSON 文本）：

```json
{ "fid": "<8 位随机 id>", "name": "a.pdf", "size": 12345,
  "idx": 0, "total": 12, "data": "<base64 分片>" }
```

约束与理由：

- **每块 24 KiB 原文**：base64 后约 32 KiB，加密后再加 MAC，仍明显小于中继
  64 KiB 单条上限（`MAX_BODY_LEN`）。块再大就会在 `too_large` 上翻车。
- **每批 40 块**：一批对应一次 WS 连接，而中继的速率限制是**每连接 120 条/分钟**。
  40 只是留了三倍余量的保守值——批太大会被限流，表现是"传一半失败"。
- **20 MB 上限**：约 854 条消息。再多就不该走消息通道了（见 4.7）。
- **接收端按 `idx` 定位写临时文件**（`RandomAccessFile`），不是攒在内存里：
  20 MB 攒内存就是 20 MB 常驻 + 大量小对象的 GC 压力，低端机直接 OOM。
  乱序到达无所谓，重复块直接忽略，收齐再 rename 成正式文件。
- **没有断点续传**：中断就得重发。这是 P1。

### 4.5 三条安全措施

1. **填充**：明文补到 16 字节边界。不填充的话，"嗯"和一句长话的密文长度差太明显，
   中继能猜出内容量级。
2. **去重**：接收方保留最近 1024 条消息 ID，命中即拒绝。防重放。
3. **棘轮本身**：Olm 会拒绝重复的密文（同一个 ratchet key 只能用一次），这是第二道防线。

### 4.6 已验证的行为（对应 `secure` 的 34 个测试）

- 双向多轮往返，棘轮持续前进
- 相同明文两次加密，密文不同
- 重放被拒
- 篡改一个字节被拒
- 同一 OTK 的第二次入站被拒
- 会话建立前加密会给出可读的错误提示
- 多会话并存：重新扫码添加不覆盖旧会话，在途消息仍可解
- 单会话落盘写旧格式（保证新旧版本互通），多会话写数组

### 4.6.1 安全码（v0.6.0）

双方身份公钥（Ed25519，即 43 字符 ID）**按字典序排序**后拼接，加域前缀
`anonchat-safety-v1|` 做 SHA-256；把摘要按 5 字节一组取模 10^5 展开，
不足 60 位就再 hash 一轮，最终得到 **60 位十进制数字**（12 组 × 5 位）。

```
code = first60( digits( sha256("anonchat-safety-v1|" + min(pkA,pkB) + "|" + max(pkA,pkB)) ) )
```

几个设计选择：

- **排序**：两边"我的/对方"的位置是反的，不排序永远算不出同一个数。
- **只用身份公钥，不用 Olm 会话密钥**：会话会因重新扫码而重建，身份不会。
  安全码跟着会话变的话，用户没法长期记住"上次核对过"。
  代价是它证明"身份没被换过"，而不是"每条会话都干净"。
- **中间人必然露馅**：能让两端各建一条独立会话的攻击者，两边算出的码必然不同。
- **核对状态怎么存**：客户端记 `verified` + 核对当时的码。当前码与记录不一致时
  标记自动失效（等价于"对方换身份了"）。

客户端入口：会话页点标题 → 显示 3 行 × 20 位；`cli safety --dir <dir> --peer <名字>`
打印同一个数，供跨端核对与自动化测试（Rust 侧 `secure::safety_number` 有单测保证
顺序无关、确定性、纯数字）。

### 4.7 还没做的

- **多设备**：明确不做
- ~~安全码比对~~：v0.6.0 已做（见 4.6.1），剩余的是邀请码签名
- **文件断点续传 / 独立传输层**：现在走消息通道，中断就得重发，20 MB 已是上限
- **固定分桶填充**（现在只按 16 字节对齐，仍泄露量级）：P0 再权衡带宽

## 5. 部署

```
客户端 ── wss://relay.example.com:443 ──> Caddy ──> 127.0.0.1:8080 (relay)
```

Caddy 配置：

```
relay.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

不想备案域名时：IP 直连 + 自签证书 + **客户端固定证书指纹**。
这要求协议层支持"信任的不是 CA，而是某个指纹"，P0 实现。

## 6. 版本与兼容

- 协议版本只在 `new` 帧里传。中继不维护版本协商状态机——简单优先。
- 加字段：JSON 默认忽略未知字段，可以直接加。
- 改语义：必须升版本，并让旧客户端**明确失败**，不要"尽力兼容"。

## 7. 已知弱点（不要假装没有）

| 弱点 | 影响 | 计划 |
|---|---|---|
| 邀请码无签名 | 中间人可替换邀请码（需能拦截带外渠道） | 已补安全码比对（v0.6.0）；签名仍待做 |
| 无填充 | 密文长度泄露明文大致长度 | P0：固定分桶填充 |
| 队列 ID 长期不变 | 长期地址可被关联 | P1：队列轮换（每次上线换新队列并通知联系人） |
| 中继知道"队列有消息"的时间 | 流量分析可推测活跃时段 | 后续：延迟投递 + 批量拉取 |
| 无多设备 | 换设备需重新加好友 | 明确不做（与匿名性冲突） |
| 一次性密钥只能被消费一次 | 若对方本地会话已丢失（重装/清数据），他再发来的预共享消息就解不开，且**无法自动恢复** | 需要在 UI 上提示"对方可能重装了，请重新互加" |
| 中继重启丢队列 | 内存存储 | P0：落盘 |

### 集成时踩到的坑（记下来省得再踩）

`vodozemac` 输出的是 **无填充的标准 base64**（Matrix 惯例），而邀请码格式约定用 base64url。
两边不统一会导致邀请码在校验阶段就被拒。现在 `secure` 在边界处统一做一次转换，
并加了 `bundle_fits_invite_format` 测试守住这个边界。
