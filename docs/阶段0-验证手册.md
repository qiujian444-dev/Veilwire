# 阶段 0 验证手册（go/no-go）

> 配套文档：`去中心化匿名聊天软件-可行性方案与技术规划.md`（v0.4）
> 目标：用 1~2 周时间，用最小成本回答四个问题。**任何一项不过关，都要停下来改方案，而不是继续写业务代码。**

| 编号 | 要回答的问题 | 不过关的后果 |
|---|---|---|
| 0.1 | 手机之间能不能直连（不走中继） | 所有通话和文件传输都要过 TURN，带宽成本翻倍，延迟变差 |
| 0.2 | 境内 443 长连接稳不稳 | 消息根本发不出去，产品不成立 |
| 0.3 | 息屏后长连接还活着吗 | 收不到消息，产品退化成"打开才同步" |
| 0.4 | 音视频能不能通 | 砍掉通话功能，或改用第三方 SFU（违背去中心化定位） |

## 0. 环境准备

本机已确认可用的组合（Windows）：

```bash
# Rust 工具链：直接用 toolchain 里的二进制，不要依赖 ~/.cargo/bin 的 shim
TC="$HOME/.rustup/toolchains/stable-x86_64-pc-windows-msvc"
"$TC/bin/cargo.exe" --version          # 本机实测 1.98.1

# MSVC 链接器（本机已装 VS2022 BuildTools）
export PATH="/c/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/VC/Tools/MSVC/14.44.35207/bin/Hostx64/x64:$PATH"
```

> ⚠️ **路径不能含中文**。本项目目录名是中文，`rustc` 链接阶段会因路径编码失败。
> 解决办法：把 `rust/` 复制到纯 ASCII 目录再编译，target 也放那边。

```bash
mkdir -p /c/anonchat-build/src
cp -r "rust/." /c/anonchat-build/src/
cd /c/anonchat-build/src && CARGO_TARGET_DIR=/c/anonchat-build/target "$TC/bin/cargo.exe" build --release
```

产物：
- `/c/anonchat-build/target/release/punch.exe`
- `/c/anonchat-build/target/release/relay.exe`

Android 端用 Android Studio（Ladybug 及以上）打开 `android/stage0`，装 JDK 17、SDK 35。

## 0.1 UDP 打洞与 NAT 映射行为

### 先测 NAT 类型（5 分钟，最能说明问题）

在一台有公网 IP 的机器上（境外 VPS 或家里有公网 IPv6 的机器）：

```bash
punch serve --port 7000
```

测试机执行：

```bash
punch nat --server <服务器IP>:7000
```

输出判读：

| 输出 | 含义 | 打洞预期 |
|---|---|---|
| `nat=eim` | 端点无关映射 | 成功率高，IPv4 也能打 |
| `nat=symmetric_like` | 依赖目标端口（对称型） | 需要同时发包，失败率高，TURN 兜底 |
| 两个外部 **IP** 都不同 | 严格对称 / 多出口 | 基本不可打，必须 TURN |

**先跑这一条，比盲目打洞有用得多。** 如果测出来大面积是对称型，直接按 40% TURN 比例做预算。

### 再测实际打洞

两端各跑一个（id 互换）：

```bash
# A 端
punch client --server <服务器IP>:7000 --id a --peer b --secs 20
# B 端
punch client --server <服务器IP>:7000 --id b --peer a --secs 20
```

结果行：

```
RUN id=a peer=b direct=true first_ms=312 recv=97 sent=100
```

### 测试矩阵（每种组合至少 20 组）

| 组合 | 说明 | 目标直连率 |
|---|---|---|
| 同运营商 4G ↔ 4G | 主力场景 | ≥80% |
| 跨运营商 4G ↔ 5G | 主力场景 | ≥60% |
| 4G ↔ 家宽 Wi-Fi | 常见场景 | ≥50% |
| 家宽 ↔ 家宽 | 次要场景 | ≥40% |

**汇总方式**：把所有 `RUN` 行存进一个 txt，数 `direct=true` 的占比。

> Android 上跑这两个 demo：用 `cargo-ndk` 交叉编译成 `.so`，由一个小测试 App 调 JNI；
> 或者临时用 Termux 装 Rust 直接跑。阶段 0 追求快，Termux 更省事。

## 0.2 境内 443 中继稳定性（72 小时）

### 起服务

在一台境内云主机上（1C1G 够用）：

```bash
relay serve --addr 127.0.0.1:8080
```

### 前面挂 TLS

**不要在自己代码里做 TLS。** 用 Caddy，自动签发和续期证书，自动处理 WebSocket 升级：

```
# /etc/caddy/Caddyfile
relay.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

这样对外就是一个标准的 443 HTTPS 站点，路径 `/` 走 WebSocket。

> **备案的现实问题**：域名解析到境内 IP 需要 ICP 备案。
> 社区自建时如果不想备案，有两个选择：
> ① 用 IP 直连 + 自签证书，客户端按**证书指纹固定（certificate pinning）**校验；
> ② 用境外域名 + 境内反代（仍需合规评估，不建议）。
> 方案①更符合"官方不运营、社区自建"的定位，**建议 P0 就支持证书指纹固定**。

### 压测

```bash
# 本机先自测
relay load --url ws://127.0.0.1:8080 --clients 20 --secs 300

# 真实验证（在境内云主机上跑，或从多个地区发起）
relay load --url wss://relay.example.com --clients 50 --secs 259200 --ping 30
```

（72 小时 = 259200 秒。建议至少 3 个不同运营商的出口各跑一组。）

### 判读

```
SUMMARY clients=50 secs=259200 drops=12 online_ratio=0.9991 ping_avg_ms=48.3 est_drops_per_day=2.00
VERDICT PASS
```

通过标准：**`est_drops_per_day` 折算到"每条连接每天掉线 < 1 次"**。
如果白天正常、晚上掉线集中，是国际链路拥塞或运营商 QoS，检查是否节点不在境内。

## 0.3 Android 后台存活（最关键，24 小时）

> **更新（2026-10-20）**：这一项现在用真实客户端 `dist/anonchat-0.1.0-arm64.apk` 测，
> 不用再单独编 `android/stage0` 那个 demo 了。操作步骤见 `docs/安装与验收.md` 第 5.2 节。
> 下面的原始步骤保留作参考。

### 编译

Android Studio 打开 `android/stage0` → Run 到真机。**必须真机，模拟器测不出 Doze 和 ROM 杀后台。**

### 逐机型操作表（每台都要做）

| ROM | 路径 | 说明 |
|---|---|---|
| 小米 / Redmi | 设置 → 应用设置 → 应用管理 → 本应用 → 省电策略 → **无限制**；自启动 → 开 | MIUI 的"省电策略"是独立于 AOSP 白名单的第二道锁 |
| 华为 / 荣耀 | 设置 → 应用 → 应用启动管理 → 本应用 → 关闭"自动管理"，勾选手动管理三项 | EMUI 的"自动管理"会覆盖 AOSP 白名单 |
| OPPO / 一加 / realme | 设置 → 电池 → 应用耗电管理 → 本应用 → 允许后台运行 + 允许自启动 | ColorOS 还有"智能省电"总开关 |
| vivo / iQOO | 设置 → 电池 → 后台高耗电 → 允许；i管家 → 应用管理 → 自启动 | |
| 原生 / Pixel | 设置 → 应用 → 本应用 → 电池 → **不受限制** | 只需 AOSP 白名单 |

App 内已内置跳转按钮（"打开厂商自启动设置"）。

### 测试协议

**A 组（授白名单）**

1. 打开 App → 申请白名单 → 确认状态显示"已授予"
2. 填入中继地址（`ws://` 或 `wss://`）→ 启动
3. 确认状态显示"已连接"
4. **锁屏，不要充电，静置 24 小时**（不要碰它，移动会退出 Doze，等于作弊）
5. 24 小时后打开 App，导出 `Android/data/io.anonchat.stage0/files/stage0-stats.csv`

**B 组（不授白名单）**：第 1 步跳过，其余相同。这组数据用来知道"最坏情况有多坏"，决定 onboarding 文案写多重。

### 判读

CSV 每 5 分钟一行：

```csv
time,uptime_secs,reconnects,connected,whitelisted,rtt_ms
2026-10-20 03:20:00,300,0,1,1,42
2026-10-20 03:25:00,600,0,1,1,45
...
```

- **通过（A 组）**：24 小时内 `reconnects` 增量 ≤ 2，且收到消息延迟 < 60s
- **不通过**：`reconnects` 每小时都在涨，或 `connected` 长期为 0

> 这一项如果 B 组表现很差（预期会），不是 bug，是 Android 的既定行为。
> 要做的是把它变成产品设计的一部分：**onboarding 里用大白话讲清楚，并在 UI 上显示"上次同步时间"而不是假装实时。**

## 0.4 WebRTC 音视频

阶段 0 不用自己写采集编码，直接用现成 demo 验证链路：

1. **TURN 自建**：境内云主机装 coturn
   ```bash
   # /etc/turnserver.conf 关键项
   listening-port=3478
   tls-listening-port=443
   realm=relay.example.com
   fingerprint
   lt-cred-mech
   user=test:test
   ```
2. **客户端**：用 `stream-webrtc-android` 的 sample app（或 LiveKit 的 example），
   把 ICE servers 配成「境内 STUN + 自建 TURN」，两端真机互拨。
3. **记录**：30 通电话，每通记录
   - 是否直连（看 selected candidate pair 的 type：host/srflx = 直连，relay = TURN）
   - 接通耗时（点呼叫 → 听到声音）
   - 通话中 MOS 主观分（1~5）

通过标准：**接通率 ≥95%，MOS ≥3.5，TURN 回落时延 <200ms。**

> ⚠️ 别用 `org.webrtc:google-webrtc`，那个官方 AAR 早已停更。
> 用社区维护的 `io.github.webrtc-sdk:android`（stream-webrtc-android）或 LiveKit Android SDK。
