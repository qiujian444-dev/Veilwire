# 中继自注册 + 客户端自动发现：实测可行性与设计

> **结论：可行，方案成立。** 但机制必须是 **BEP5（announce_peer / get_peers）**，不是 BEP44。
> 本文全部数据来自本机实测（2026-10-23，大陆家庭宽带），脚本 `scripts/dht_relay_discovery.py` 可复现。
>
> 修正记录：初版评估曾判定"不可行"，其中"0 peers"的结论是**我方解析 bug** 导致的误判
> （`values` 是 6 字节字符串的 list，被当成单个 bytes 处理）。修正后 BEP5 完全可用，特此更正。

## 2. 为什么必须是 BEP5，不能是 BEP44

这是整个方案的关键分水岭，两者不能混用。

### BEP44 mutable 项：结构性不合适

存储键 = `SHA1(ed25519_pubkey + salt)`，两个硬限制：

1. **必须先知道发布者公钥才能查**。客户端想"发现从未听说过的中继"，无法从任意公钥反推。
2. **一个 key 只接受同一密钥的单调 `seq`**。多个中继无法共用一个 key —— 后写的会把先写的覆盖掉。

实测也印证了：BEP44 `put` 返回 17/20 成功，但**立即回读 0/17**——
节点接受了签名却没有真正落库（或只在极短窗口内可见）。同节点的 A/B 对照更清楚：

```
A 不可变项：put 后回读 → 命中 ✓
B 可变项：  put=OK，put 后回读 → v=None ✗（keys 只有 id/nodes/p/token）
C 带 seq=0 的 get → v=None ✗
```

### BEP5 peer 发现：天生匹配

```
中继:   announce_peer(info_hash = SHA1("veilwire-relays-v1"), port = 3478)
客户端: get_peers(info_hash)  →  [(ip, port), (ip, port), ...]
```

- 任意多个节点可以注册到**同一个** infohash，天然是"多中继目录"
- 客户端只需知道 infohash 常量（编译进 App），无需任何公钥
- 标准 BitTorrent 生态共用，节点实现成熟

## 3. 三个必须理解的约束

### 3.1 IP 不可伪造，由 DHT 按来源判定（这是优点）

实测：我指定 announce `203.0.113.10`，但三个节点查回的都是 `('198.51.100.20', 3478)`——
**端口是我给的，IP 是我的真实出口 IP**。

含义：

- 中继**无法**把别人的 IP 注册成自己的（防投毒、防陷害）
- 中继**必须**从它要对外服务的那个 IP 上发出 announce
- 若中继在 NAT 后面，注册进去的是 NAT 出口 IP —— 所以中继必须有独占公网 IP 或完整端口映射

### 3.2 记录会过期，必须周期重播

BEP5 peer 记录由存储节点按 TTL 丢弃（通常 15~30 分钟量级，各实现不同）。
中继需要**每隔约 10 分钟重新 announce 一轮最近的 k 个节点**。

这不是负担：中继本来就是常驻进程，加一个定时任务是自然的事。
但必须监控"最近一次 announce 成功数"，为 0 就告警。

### 3.3 6881 端口被注入投毒，必须做防御

实测发现：发往 **6881 端口**的 KRPC 查询会收到伪造响应，特征是
**8 条记录 node_id 与 ip:port 完全相同**（真实 Kademlia k-bucket 不可能这样）。

对照实验证明这是按端口触发的路径注入：

```
真实DHT节点:6881        → 8条/去重1   ← 被注入
同一IP:11111            → 超时        ← 干净
同一IP:12345            → 超时        ← 干净
1.1.1.1:6881            → 超时
203.0.113.99:6881       → 超时        ← 保留地址不存在，说明只有特定路径被注入
```

**防御要求**（三条都必须做）：

1. **来源 IP 校验**：响应来源必须等于查询目标，否则丢弃
2. **事务 ID 校验**：`t` 字段必须匹配，否则丢弃
3. **重复记录检测**：一批 `nodes` 里 node_id 或 ip:port 全相同 → 整包丢弃

实测中，带这三种防御后爬取完全正常（得到 674 个可达节点，丢弃伪造 0 次——
说明只要从干净端口（非 6881）出发就基本遇不到注入）。

### 3.4 bootstrap 域名污染，必须内置缓存种子

实测 bootstrap 域名状态（多次解析结果不稳定）：

```
router.bittorrent.com   → 67.215.246.10 / 128.121.146.109   超时
router.utorrent.com     → 31.13.88.169 (Facebook 段!)       超时
                        → 173.244.217.42 / 108.160.173.207  超时
dht.libtorrent.org      → 98.159.108.57 / 128.242.240.221   超时
dht.aelitis.com         → 69.63.176.143 / 128.242.240.189   超时
dht.transmissionbt.com  → 212.129.33.59 / 87.98.162.88      有响应
```

10 个种子域名里通常只有 1~2 个可用，且**解析到的 IP 每次不同**（真域名不会这样）。

**关键经验**：把上一次成功连上的节点**持久化到磁盘**，下次启动优先用它们做种子。
实测：9 个缓存节点（上次 BEP44 put 成功的那批）**全部在线**，
靠它们单轮就爬到 674 个节点——完全绕开了 bootstrap 域名污染。

## 4. 建议的落地方案

### 4.1 中继侧（`rust/crates/relay`）

新增 `--dht-announce` 开关，默认关闭。开启后：

```
每 10 分钟：
  1. 若节点表为空 → 用内置种子 + 磁盘缓存种子启动爬取
  2. 迭代爬取，收敛到离 target=service_key 最近的 ~20 个节点
  3. 对它们逐个 get_peers 拿 token → announce_peer(port=对外服务端口)
  4. 记录本轮成功数；连续 3 轮为 0 → 打 WARN 日志
  5. 把真实响应过的节点写入 <data>/dht-nodes.json，下次启动直接用
```

频率控制：**10 分钟一次**足够（BEP5 TTL 通常 ≥15 分钟），别打太密。

### 4.2 客户端侧（Android + Rust client）

```
启动时（后台、不阻塞 UI）：
  1. get_peers(SERVICE_KEY) 迭代查询，最多 8 轮 / 60 次查询
  2. 收集到的 (ip, port) 转成 ws://ip:port/ws 候选
  3. 用现有 relay_probe 并发测速
  4. 与「邀请码里的中继」「内置快照」「上次用的中继」合并去重
  5. 按优先级尝试：邀请码 > 用户手动 > DHT 发现 > 内置快照
```

**关键设计原则：DHT 只作补充来源，永不作为唯一来源。**
理由：DHT 查询有延迟（实测冷启动 2~8 轮、十几秒），断网/被墙时必然失败。
必须保留邀请码和内置快照作为兜底。

### 4.3 服务键

```rust
// 编译期常量，改一次全网失效，需谨慎
const SERVICE_KEY: [u8; 20] = sha1(b"veilwire-relays-v1");
```

不要用可配置的 key，否则等于又引入一个弱中心。

## 5. 必须正视的风险

### 5.1 中继地址变成公开可枚举（最重要的权衡）

一旦 announce，任何人 `get_peers(SERVICE_KEY)` 就能拿到**全部中继清单**。
好消息是此刻只有 1~2 个，但这是设计性的暴露。

**这是对 README 里那段论证的实际挑战**：

> Session hardcodes its node list as public IPs. Block those IPs and the whole network dies.

必须承认：**公开 = 可被封**。缓解手段：

1. **中继数量要够多**，单点被封不影响整体——这是唯一真正的解法
2. DHT 里只注册 **WS 端口**，TURN 端口另走邀请码分发，不上公网目录
3. 允许用户完全关闭 DHT 发现（设置项默认开启但可关）
4. 客户端不要"全量拉取后逐个上报"，避免成为放大攻击的帮凶

**建议在 README 里如实写明这个权衡**，而不是宣称"更安全"。诚实的文档比营销有价值。

### 5.2 中继被当成免费 TURN 滥用

公开目录意味着任何人都能用。中继侧必须保留：
- 每 IP 并发上限（已有 `--turn-max-per-ip`）
- 速率限制（已有）
- 队列容量上限

### 5.3 时间窗口：注册后多久可见

实测 announce 后**立即**从 3 个独立节点查到了，延迟可忽略。
但**过期**时间未精确测量（需要挂机观察），上线前应补一个 30 分钟~2 小时的观测。

## 6. 最终判断

| 维度 | 评价 |
|---|---|
| 技术上是否可行 | ✅ **可行，已端到端验证** |
| 是否解决"每次手输中继" | ✅ 解决，冷启动能自动发现 |
| 大陆网络是否可用 | ✅ 可用（674 可达节点、26/30 announce、14/20 get_peers 有返回） |
| 实现成本 | 中（中继侧 ~300 行 + 客户端 ~250 行 + 抗投毒逻辑） |
| 主要代价 | **中继地址公开可枚举，需要靠数量抗封锁** |
| 推荐程度 | **建议做，但作为补充来源，默认开启、可关闭，必须保留邀请码主渠道** |

### 与之前评估的差异

之前判"不可行"错了，错在两处：
1. **机制选错**：用了 BEP44（结构性不适合多中继注册），应该是 BEP5
2. **解析 bug**：`values` 类型处理错误，把真实的 peers 全丢了，误判成"网络不可用"

修正后结论完全反转：**这条路是通的，而且正是你设想的那样。**

### 实测结果（本机，大陆家庭宽带）

- 中继公布：爬到 14 个节点 → **公布成功 13 个**
- 客户端发现：从默认种子出发，40 秒内查到 `ws://198.51.100.20:18899`（自家中继）
- 用真实 Ubuntu infohash 验证 `get_peers` 通路：14/20 节点返回、共 326 个 peer

### 实现上的几个关键决定

1. **不引入新的第三方依赖**。bencode 与 KRPC 自己实现（约 300 行），
   避免为一个开关把依赖树和二进制体积拉大。
2. **查询并发化**。最初 `get_peers` 是串行的，8 个节点 × 3 秒超时 = 一轮 24 秒，
   手机冷启动实测要 60 秒以上；改成每批并发（每个任务独立 socket，避免抢包）后
   降到 25~40 秒。
3. **节点表持久化**（`<data>/dht-nodes.json`）。实测重启后 9 个缓存节点全部在线，
   单轮就能爬到几百个节点，完全绕开被污染的 bootstrap 域名。
4. **注入防御三件套**必须同时做：来源 IP 校验、事务 ID 校验、重复记录检测。
   只做其中一两个仍会拿到垃圾数据。

### TURN 凭据分发（已完成，0.15.0）

DHT 只能放 IP + 端口（BEP5 记录固定 6 字节），放不下账号密码；把固定凭据
编译进 App 又等于把 TURN 变成公开免费中继。所以做成**按需签发**：

```
客户端 → WS: GetTurn
中继   → 现生成 eph-xxxx 账号（TTL 1 小时），返回 {url, user, pass, ttl}
客户端 → 缓存到 <dir>/turn.json，剩余 <5 分钟才重新索取
```

实现要点：

- `turn/auth.rs` 里加了一张全局临时凭据表（一个进程只有一个 TURN 实例，
  用全局比把所有权在两层间传递简单得多），过期项在签发时顺手清理
- 静态 `--turn-user/--turn-pass` 仍然保留并优先匹配，方便自建 coturn 的人
- 中继没开 TURN 时回 `no_turn`，客户端明确回退到用户手填配置，不会拿到假地址
- `CallManager` 先在后台预热凭据，`iceServers()` 只读缓存——
  否则建 PeerConnection 时同步请求会卡住主线程

### 多中继回退（已完成）

之前发送只用 `relays.first()`：联系人记录里最多存 4 个中继，但只用第一个，
第一个挂了消息就发不出去，剩下三个存在磁盘上从来没被用过。

现在发送侧会**按顺序试到成功为止**，而且判断的是"投递成功"而不是"连上了"：

| 情况 | 处理 |
|---|---|
| 首位连不上 | 换下一个 |
| 首位连上但 `put` 回 `no_queue`（那台没有他的队列） | 继续换下一个 |
| 全部失败 | 明确报错，失败的加密结果**不落盘** |

投递成功的那台会被**提到首位**（只重排、不删地址），下次不再先撞一遍墙。
写盘失败只告警——消息已经投出去了，不该因为"记不住下次先试哪个"而让用户以为发送失败。

**收消息侧刻意不做回退**，这个区别必须写清楚：

- `me.relays` 的首位是"我的队列在哪台"。队列是各中继实例本地的，不跨机器共享。
- 中继的 `Sub` 对**不存在的队列是静默成功的**（只回 Ok，不补投任何积压）。
- 所以"首位连不上就换下一个"会得到比失败更糟的结果：连接正常、订阅成功、
  永远收不到消息，界面上看起来完全在线。

真要在中继之间迁移只能走 `set_relay`：在新中继重建队列，再把新地址加密推给所有联系人。
那个动作会换 qid、让所有对方重学路由，不能在一次网络抖动里自动做。
现在的行为是明确报错并指出是哪台中继连不上。

回归测试：`rust/crates/relay/tests/relay_failover.rs`（三个用例，含 `no_queue` 那一档）。

### 仍未做

- **DHT 记录过期的精确时长**未测（需挂机观察 30 分钟~2 小时）。
- 中继不可达时只有错误提示，还没有"一键迁移到另一个中继"的入口
  （`set_relay` 已经具备全部能力，缺的是 UI 和确认流程）。

## 9. 多中继下的通信模型（补记）

实现过程中顺带查清了一件容易误判的事：**双方连不同中继照样能通信**。

```
A 收消息 → 连自己的 R1，订阅自己的 qid（这是 A 的信箱）
A 发消息 → 连 B 的 R2，把密文投进 B 的 qid（这是 B 的信箱）
```

也就是说，每人把自己的信箱放在自己选的中继上，寄信时直接投到对方信箱所在的中继。
不需要共用同一台中继。

**但有两个前提**，实现时改坏过，这里记下来：

1. 联系人的 `relays` 表示「**他的**队列在哪」，不是「我在哪」。
   任何"批量改写联系人中继"的操作都会让所有对外发送打错地方（`no_queue`），
   而且界面上没有任何报错。`set_relay` 曾经就是这么写的，已修。
2. 陌生人回信时，`reply_relays` 的**顺序**决定成败（发送只用 `first()`）。
   必须把对方自报的中继放第一位，自己的中继只能作为兜底排在最后。
   早期实现反了，导致陌生人永远回不了信。已修，并有回归测试
   （`rust/crates/relay/tests/cross_relay_routing.rs`）。

这两条都有回归测试锁着，改路由相关代码时会直接失败。

## 10. 生产部署验证（0.15.0，公网单台中继）

在一台公网 Ubuntu 机器上按部署指南跑起来之后，从本地网络（大陆家庭宽带）实测：

| 检查项 | 结果 |
|---|---|
| 中继公布 | `[dht] 已公布：WS 端口 8080 成功 11 个节点；TURN 端口 3478 成功 11 个节点（候选 16）` |
| 记录确实落库 | 直接向中继自己爬到的 16 个节点查询：**11 个**持有 `WS 记录`，**11 个**持有 `TURN 记录` |
| 冷启动反查 | `relay_check.py <公网IP>:8080 --dht` → 爬到 279 个活跃节点后查到该中继 |
| WS / 心跳 / 新建队列 | 全通（`new` 返回 qid，TTL 30 天） |
| TURN 临时凭据 | `get_turn` 返回 `eph-xxxxxxxx`、TTL 3600；用它跑 `turn_probe` 到 Allocate 成功且 MESSAGE-INTEGRITY 校验通过 |

两个过程中确认的坑：

1. **`--dht-announce` 必须填"客户端实际连的那个端口"**。这台是 host 网络直连 8080，
   所以填 8080；如果前面挂了 Caddy 反代 443，就必须填 443，否则公布出去的是个死端口。
