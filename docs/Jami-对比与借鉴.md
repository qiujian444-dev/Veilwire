# Jami 对比与借鉴分析

> 目的：把 Jami（GNU 官方 P2P 通讯项目，前身 Ring）拆开看一遍，判断哪些设计与功能值得
> Veilwire 借鉴、哪些是它的历史包袱不要碰。结论按「值不值得做」排序，不是按 Jami 的功能表排序。

## 0. 一句话结论

Jami 的三大真正优势是**多设备消息树同步**、**局域网无网直连**、**一键把设备变成会议宿主**；
它的三大代价是**DHT 依赖 bootstrap 节点**、**git 做消息存储**、**移动端依赖厂商推送**。

Veilwire 现在最该补的不是"DHT 全球寻址"，而是**局域网直连**和**多设备/换机历史**——这两个
投入产出比最高，而且不破坏现有"无中心目录"的定位。

---

## 1. Jami 是什么

模块化架构：**daemon（libjami，C++，全部业务逻辑）+ 多个前端 GUI（Qt/Android/iOS）通过 D-Bus 通信**。
Veilwire 的 Rust core + JNI + Compose 在架构上已经对齐这个分法，不需要改。

| 组件 | 作用 |
|---|---|
| `jami-daemon` | 核心：账号、通话、会话、Swarm 同步、加密（GPLv3） |
| `opendht` | Kademlia DHT，无服务器寻址（**MIT 许可**，有 Rust/C/Python 绑定） |
| `jami-client-android` | Android UI（Kotlin） |
| `jami-nameservice` | 区块链用户名注册（Solidity + HTTP 网关，GPLv3） |

### Swarm 的关键设计（最值得研究的部分）

Jami 用 **git 的 Merkle DAG** 来存会话，不是用"消息列表"：

- 每条消息 = 一个 commit，commit 里带 `prev` 指针 → 天然有全序，不怕乱序到达
- 每个成员设备各持一棵子树，缺哪段就 pull 哪段 → 增量同步，不用拉全量
- 成员/设备/证书都放在仓库目录里（`/members`、`/devices`、`/admins`）→ 新人加入靠"验证并合并你的分支"
- 提交用设备密钥签名 → 非抵赖，任何人可回放验证整段历史
- 成员/设备变更也是 commit → 群成员管理不需要中心服务器裁定

Jami 团队自己写过一篇文章解释为什么要弃用"逐条消息投递 + 等确认"的旧模型，四个理由很有说服力：
**消息无序、无法区分同内容消息、发送方多设备只有一台留有副本、无法重试补投**。
Veilwire 现在的模型恰好踩在这四点中的第 3、4 点。

## 2. 值得借鉴的功能（按优先级）

### P0 — 局域网直连（投入最小、价值最大）

**Jami 怎么做的**：同网段设备通过 mDNS/组播发现彼此，直接建立 P2P 连接，完全不需要互联网。
Jami 官网把它当作头号卖点："Users who are on the same local network can communicate with Jami
even if they are disconnected from the internet."

**Veilwire 现状**：`rust/crates/punch` 只有 UDP 打洞和 NAT 探测，**没有任何局域网发现能力**。
断网 = 全功能不可用（消息排队在中继，通话直接失败）。

**为什么最有价值**：
1. 中继被封/被打时，局域网内仍然能用——这直接回应了 README 里"俄罗斯封 IP"那段论证
2. 通话不再依赖 TURN，同 WiFi 下延迟从 100ms+ 降到 5ms 级
3. 实现成本低：mDNS（`mdns-sd` crate）+ 复用现有 Olm 会话 + 复用现有 WebRTC 直连路径
4. 不引入任何新的信任假设：设备身份还是 Ed25519，加密会话照旧

**做法**：新增 `crates/lan`，广播 `_veilwire._udp.local`，TXT 记录只放 `dh` 指纹（不放名字，
否则等于局域网内实名广播）。连接建立后走完全相同的加密握手。UI 上给个"局域网"标识。

**风险**：中低。注意点是有的人在公司/校园网里不希望被同网段设备发现，**默认关闭、手动开启**。

---

### P0 — 网络切换通话不断（Jami 的 Call Handover）

**Jami 怎么做的**（这块它的工程严谨度值得抄）：
默认网络变化或 SIP 通道断开后，**在 20 秒窗口内重建通道并重启 ICE，通话保留**。
防重放做得很细：`X-Jami-Handover-Generation` 单调递增，旧代值的 re-INVITE 直接 491 拒绝，
迟到的 SDP/ICE 结果不能提交到新一代，队列里的 offer 完成时还要再校验一次代际。

**Veilwire 现状**：`CallManager` 已有 `forceReconnect()` + `NetworkCallback` 自动触发，
但**没有代际（generation）概念**。后果很实在：网络抖动时连续两次重启，前一次的
offer/answer 迟到到达，会把当前会话状态覆盖掉——表现就是"通话连着但没声音"。

**做法**：给 `client::call` 的状态机加 `generation: u64`，所有 SDP/candidate 事件带上代际，
不匹配就丢弃。约 100~150 行改动，不需要新增依赖。**这是纯健壮性修复，建议优先于任何新功能。**

---

### P1 — 多设备 / 换机历史（Jami Swarm 的真正价值）

**Jami 怎么做的**：不是"服务器帮你同步"，而是**设备之间互相 pull**。新设备上线后通过
`sync://DEVICE_ID` 通道和旧设备直连，先报告自己已知的会话列表，再按缺补拉。
同账号多设备共享同一棵树，任何一台发的消息，其他台都能看到（含"已发送"副本）。

**Veilwire 现状**：结构性缺失。`proto` 是"接收方生成队列 + 发送方 put"的无标识队列模型，
**发送方自己的副本只存在本机**。这意味着：
1. 换手机 = 历史全丢（12 词只能恢复身份，不能恢复消息）
2. 多端同时用 = 两个独立人格，互相看不见
3. 发给对方的消息，自己另一台设备永远不知道

**借鉴方式（重要：不要照抄 git）**：

Jami 用 git 是合理的，因为它的会话本身就是"多方协作编辑一份文档"；但代价也很明显——
Jami FAQ 里自己有条目 "Why aren't my sent messages showing up on all linked devices?",
移动端同步慢、耗电也是长期抱怨点。Veilwire 只有 1:1，不需要通用 DAG。

建议**最小可行版**：
1. 每条消息加 `prev` 字段（上一条的 id），形成单链；冲突时按 `(lamport, dh)` 排序
2. 新增 `crates/device-sync`：同账号设备间通过中继的**一次性临时队列**交换"我有哪些 msg id"
   （布隆过滤器 + 差集），再逐条补拉
3. 消息体仍然是 Olm 密文，同步时用**设备间共享的账号级对称密钥**再包一层
4. UI 加一个"导出/导入聊天记录"（加密 zip），先解决"换机"这个最痛的点，多端实时同步放后面

**投入**：中等偏大（1~2 周量级）。但这是"能不能当日常主力软件"的分水岭——
没有这个，用户换机就流失。

---

### P1 — Presence / 已读回执 / 输入状态

**Jami 怎么做的**：三种状态分得很清楚，这个区分值得学：
- 🔴 本机没连上 DHT
- 🟠 对方至少一台设备在 DHT 上宣告了（"看起来可达"，NAT 可能打不通）
- 🟢 已和对方某台设备建立直连（"确实可达"）

它明确把"在线"拆成"可达性"和"连通性"两件事，比单一绿点诚实得多。

**Veilwire 现状**：都没有。`secure::kind` 里只有 `text` / `call.*` / `file`。

**做法**：复用 `send_control` 通道加三种轻量类型（`presence` / `receipt` / `typing`），
都是**阅后即焚、不落盘**的控制帧。成本很低（估计 200 行以内），但聊天软件的体感提升极明显。
注意：typing/receipt 默认开启要慎重，匿名软件的元数据泄露风险要跟用户说清楚，
建议做成开关且默认**只发 typing 不发 receipt**（回执等于告诉对方你在看屏幕）。

---

### P2 — Rendezvous Point（一键把设备变成会议宿主）

**Jami 怎么做的**：在账号创建向导里就能建一个"会合点"账号，它本身像一个常驻的会议参与者。
邀请的人随时进来开会，**即使创建者本人不在线也没关系**（只要那台设备连着网）。

**Veilwire 可借鉴的点**：这个交互设计比"部署服务器"友好太多。Veilwire 已经有 relay 二进制，
可以做成：**手机上点一下"开一个群"，App 就在本机跑一个轻量会话宿主**（复用 relay 的队列逻辑，
只服务这个群的成员），退出即销毁。这条路能绕开"群聊要不要中心服务器"的争论。

**但要先想清楚**：群聊涉及密钥分发（N 人 N-1 次加密，还是 Sender Key）、成员变更、
历史对新人可见性。Veilwire 现在是严格 1:1 的 Olm 会话，改群聊不是加个字段的事。
**建议在 P0/P1 做完之后再动，且先做"小群 + Sender Key"而不是大群。**

---

### P2 — 其他可以抄的小东西

| 功能 | Jami 的做法 | Veilwire 借鉴价值 |
|---|---|---|
| 屏幕共享 / 媒体流 | 通话中切换视频源为屏幕或媒体文件 | 中。Android 用 MediaProjection，工作量不大，但要注意隐私提示必须显眼 |
| 音视频留言 | 录一段直接发，不用打字 | 低（Veilwire 已有语音消息，视频留言优先级低） |
| 通话中动态布局 | 点谁就把谁放大 | 低（1:1 用不上，群通话才需要） |
| 账号/会话备份导出 | 导出完整账号 + 会话历史 | **高**，但已并入 P1 的"导出/导入" |
| 多档码率自适应 | 50kB/s 就能跑音视频，10kB/s 纯语音 | 中。Veilwire 应该测一下弱网下的实际码率下限并写进 README |
| 中继/连接诊断 | 状态圆点 + 详细错误说明 | 中。Veilwire 已有 `relay_probe`，可以把结果做成更友好的诊断页 |

## 3. 明确不要抄的部分

### ❌ 全球 DHT 寻址（OpenDHT）

理由不是技术不行，而是**它和 Veilwire 的定位冲突**：

1. **DHT 也要 bootstrap 节点**。Jami 官方 bootstrap 是 `bootstrap.jami.net`——这就是一个中心点。
   封掉它，新设备就进不了网。Veilwire 现在的"邀请码里带中继地址"反而更抗封：中继可以随便换，
   不需要任何公共种子。
2. **移动端最后还是要厂商推送**。Jami 的 Android 依赖 FCM 唤醒，中国境内基本不可用。
   Veilwire 用常驻前台服务 + 自己的中继，这条路虽然"土"，但在目标场景下更能跑通。
3. **DHT 会暴露你的 IP 给随机节点**。对匿名软件是净负面。

**唯一可考虑的子集**：把"中继地址发现"做成**可选的自建轻量目录**（一个静态 JSON 托管在任意
HTTP 上，客户端可配置多个源、可完全不用）——解决"朋友发我一个中继地址太麻烦"，
而不是做全球 P2P 网络。这属于产品体验优化，不是架构改造。

### ❌ 用 git 存消息

git 的优势是历史可验证、增量拉取，代价是移动端同步开销大、仓库随历史单调膨胀、
每次同步要跑对象打包。Jami 自己都在 FAQ 里解释同步问题。
**借鉴它的数据模型（prev 指针 + 增量补拉），不要借鉴它的存储引擎。**

### ❌ SIP 兼容 / 企业账号体系（JAMS）

Jami 做这两个是为了进企业市场（它背后是家咨询公司）。Veilwire 没有这个商业目标，
引入 SIP 会带来巨大的协议表面积和安全审计负担。不做。

### ❌ 扩展平台 / 插件商店

Jami 宣传了很多年，实际生态没起来。在核心体验没打磨好之前做插件平台是本末倒置。

## 4. 许可与法务

| 项目 | 许可 | 对 Veilwire（AGPL-3.0-only）意味着什么 |
|---|---|---|
| `jami-daemon` | GPL-3.0-or-later | 与 AGPLv3 双向兼容，可以组合，但**组合作品整体受 AGPLv3 约束**，须保留版权声明与来源 |
| `opendht` | **MIT** | 可直接作为依赖使用，只需保留版权声明（如果将来真要用） |
| `jami-nameservice` | GPL-3.0 | 同上 |

**工程建议**：**只借鉴设计思想与协议行为，不复制代码**。理由不是法律不允许，而是
1. C++ → Rust 的移植本来就等于重写；
2. 一旦引入 GPL 代码，未来想调整许可（比如给应用商店做例外）就没有余地了；
3. Jami 的设计文档（Swarm 设计文档、同步协议文档）是公开的，照着设计自己实现最干净。

如果要引用它的协议行为（比如 handover 的代际规则），在代码注释里注明
"design inspired by Jami's Call Handover (GPLv3)，独立实现"即可，这是社区的通行做法。

## 5. 建议的执行顺序

```
第 1 步（1~2 天）    通话代际防护        —— 纯 bug 修复，先止血
第 2 步（3~5 天）    局域网直连 mDNS      —— 最高性价比的新能力
第 3 步（3~5 天）    typing + presence    —— 体感提升最快
第 4 步（1~2 周）    加密导出/导入         —— 解决换机流失（P1 的最小切片）
第 5 步（1~2 周）    多设备增量同步        —— 真正的架构升级
第 6 步（待定）      小群 + Sender Key     —— 想清楚密钥分发再动
```

前两步做完，Veilwire 就已经比现在"抗封锁 + 弱网可用"高一个档次，而不用碰任何中心化妥协。
