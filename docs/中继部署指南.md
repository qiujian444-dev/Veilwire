# 中继部署指南

> 面向：想给社区跑一台中继的人。
> 定位前提：**官方不运营任何公共服务**。中继由谁部署、部署在哪、对谁负责，都是部署者自己的事。
> 本文只讲技术，不含任何合规建议——请自行确认当地法律要求。

---

## 1. 这台机器要干什么

中继只做三件事：

1. 按队列 ID 存密文（它看不懂内容，也看不到发送方）；
2. 有人订阅时把新消息推过去；
3. 到 TTL 或收到 ACK 时删除。

它**不**存用户表、**不**做账号、**不**转发音视频、**不**知道谁和谁在聊。

---

## 2. 最低配置

| 项 | 建议 | 说明 |
|---|---|---|
| CPU | 1 核 | 中继基本是 IO 等待 |
| 内存 | 512MB | 队列在内存里，按"并发用户数 × 平均积压"估 |
| 磁盘 | 10GB | 追加日志，30 天 TTL，实测约 1 万用户/月 1~3GB |
| 带宽 | 5Mbps 起 | 纯文本中继很省；文件走 P2P 不经过这里 |
| 系统 | Linux x86_64 | Windows 也能跑，但生产建议 Linux |

> 容量粗估：**1 台 1C1G 大约能支撑 5000~10000 个活跃队列**（每人一个队列，平均积压 10 条以内）。
> 这是估算不是承诺，上线前请用 `relay load` 压一遍。

---

## 3. 部署

### 3.1 直接跑二进制

```bash
# 编译（在开发机上）
cargo build --release -p relay
# 产物：target/release/relay

# 传上去，建个专用用户
sudo useradd -r -s /usr/sbin/nologin relay
sudo mkdir -p /var/lib/relay && sudo chown relay:relay /var/lib/relay

# 跑起来（只监听本地，TLS 交给 Caddy）
sudo -u relay ./relay serve --addr 127.0.0.1:8080 --data /var/lib/relay
```

systemd 单元：

```ini
[Unit]
Description=AnonChat Relay
After=network.target

[Service]
User=relay
ExecStart=/opt/relay/relay serve --addr 127.0.0.1:8080 --data /var/lib/relay
Restart=always
RestartSec=3
# 限制它能碰的东西
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=/var/lib/relay

[Install]
WantedBy=multi-user.target
```

### 3.2 Docker

```bash
# rust/ 目录下有现成的 Dockerfile（多阶段：rust:1-slim 编译 → debian-slim 运行）
docker build -t veilwire-relay:0.15.0 ./rust

# 只做 WS 中继
docker run -d --name relay \
  -p 127.0.0.1:8080:8080 \
  -v relay-data:/data \
  veilwire-relay:0.15.0
```

镜像的 ENTRYPOINT 已经带了 `serve --addr 0.0.0.0:8080 --data /data`，
**额外的 flag 直接追加在镜像名后面**，不用再写 `--entrypoint`。
构建用了 cache mount 复用 cargo 依赖缓存，改一行代码重建时不会重编整个依赖树
（2 核机器上差 10 分钟以上）。

### 3.3 自带 TURN（通话需要，**不需要再装 coturn**）

语音/视频通话要打穿 NAT。从 0.13 起中继进程自带 TURN，同一个进程、同一个容器，
不用再单独跑 coturn。**不加 `--turn` 就是纯 WS 中继**，行为和以前完全一样。

```bash
docker run -d --name relay --network host --restart unless-stopped \
  -v /var/lib/relay:/data \
  veilwire-relay:0.15.0 \
  --turn 0.0.0.0:3478 --turn-external-ip <公网IP> \
  --turn-user <用户> --turn-pass <密码> --turn-realm <realm> \
  --turn-port-min 49160 --turn-port-max 49200 \
  --dht-announce 8080
```

三个必须记住的点：

1. **`--turn` 要绑 `0.0.0.0`**。绑具体内网 IP 的话，公网 UDP 包不会交付（这台 VPC 上实测过）。
2. **`--turn-external-ip` 必填**。服务器公网是 NAT 映射，relayed address 必须通告公网 IP，
   否则会出现“分配成功但媒体不通”这种最难查的故障。
3. **`--network host`**。TURN 要绑一整段 UDP 端口，`-p` 逐端口映射既繁琐又会破坏源端口；
   安全边界靠安全组，不靠 docker 的端口映射。

安全组要放行：`8080/tcp`、`3478/udp`、以及端口段 `49160-49200/udp`。

默认就带的安全策略（都是照 coturn 的做法）：

- **拒绝把数据中转给回环/内网地址**（TURN 是经典 SSRF 跳板）。本机联调才加 `--turn-allow-private-peers`；
- 不做匿名 TURN，没给账号密码直接拒绝启动；
- 每 IP 分配上限 8（`--turn-max-per-ip`）、分配 TTL 600s、端口段耗尽返回 486。

部署完自检：

```bash
# 一次性检查：WS 握手 → 心跳 → 索取 TURN 临时凭据 → 新建队列 → （可选）DHT 反查
python scripts/relay_check.py <公网IP>:8080 --dht

# 单独压一遍 TURN 转发
python scripts/turn_probe.py <公网IP> 3478 <用户> <密码> <realm>
```

`relay_check.py` 里的 `--dht` 会先 find_node 爬到服务键附近再 get_peers，
所以能真正回答"陌生客户端能不能自动发现我这台中继"，而不只是"端口开着"。

**关于 `turn_probe.py` 的预期结果**：在*生产*中继上，它会卡在第 4 步
`CreatePermission 400 Bad Request`——因为探测脚本拿 `127.0.0.1` 当对端，
而中继默认拒绝把数据转给回环/内网地址（SSRF 防护，见下面第 3.3 节）。
**这是正确行为，不是部署失败**：走到 Allocate 成功且 MESSAGE-INTEGRITY 校验通过，
就说明凭据和转发端口都没问题。要在本机跑满 9 步，启动时加 `--turn-allow-private-peers`。

## 4. TLS：交给 Caddy，别自己写

中继本身**不做 TLS**，只监听 `127.0.0.1`。前面挂 Caddy，自动签发和续期证书：

```
# /etc/caddy/Caddyfile
relay.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Caddy 会自动处理 WebSocket 升级，对外看起来就是一个普通 HTTPS 站点。

**为什么不自己实现 TLS**：证书续期、密码套件、协议版本、OCSP、HTTP/2 兼容——每一项都比我们手写靠谱。
中继代码保持最小攻击面，是这套架构能长期维护的前提。

## 5. 数据与备份

```
/var/lib/relay/
  queues.log        # 追加日志，启动时重放
```

- **格式**：一行一条 JSON 事件（建队列 / 投递 / ACK）。
- **崩溃恢复**：单行损坏会被跳过并计数，不会导致起不来。
- **压缩**：当日志膨胀超过有效数据量的阈值，自动重写（原子 rename）。日志里出现 `日志已压缩` 就是它干了活。
- **备份**：`queues.log` 直接 `cp` 即可，它是自包含的。

### fsync 的取舍（重要）

默认**不 fsync**：崩溃最多丢最后几秒的写入。
对 IM 可以接受——客户端没收到 ACK 会重发，丢的那几条会补回来。

要极致可靠就加 `--fsync`，代价是每条消息一次磁盘同步，吞吐掉一个数量级。
**不建议在机械盘上开**。

## 6. 域名备案的现实问题

域名解析到境内 IP 需要备案。社区部署时如果不想备案，有两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. IP 直连 + 自签证书 | 客户端按**证书指纹**固定校验，不依赖 CA | 需要客户端支持指纹固定（P0 实现） |
| B. 用境外域名 + 境内反代 | — | 合规风险高，不建议 |

**推荐方案 A**：它更符合"官方不运营、社区自建"的定位，也不依赖任何 CA。

## 7. 被封 IP 之后怎么办

这件事会发生，不是会不会的问题。准备工作：

1. **准备多个 IP**：不同云厂商、不同地域，客户端支持多中继冗余，封一个不影响整体。
2. **客户端可自定义中继**：用户能扫码加新中继，这是最后一道保险。
3. **换 IP 脚本化**：把部署做成一条命令，换机器 5 分钟能恢复。
4. **公告渠道**：新地址要能通知到用户。这就是为什么客户端必须支持手动添加中继——不能被官方列表卡死。

## 8. 看什么指标判断它是否健康

| 指标 | 正常 | 异常含义 |
|---|---|---|
| 启动日志 `恢复 N 个队列` | 平稳增长 | 突然归零 → 数据目录挂了 |
| `清理 M 个过期队列` | 每小时个位数 | 大量 → 有一批死队列，可能有人在刷 |
| `损坏行` | 0 | >0 → 上次异常退出，检查磁盘 |
| `日志已压缩` 频率 | 每天几次 | 每分钟 → 有人在大量投递后立即 ack（可能被当广播用） |
| 内存占用 | < 512MB | 持续上涨 → 订阅者泄漏或积压没清 |

## 9. 已知限制（部署前必须知道）

| 限制 | 影响 | 计划 |
|---|---|---|
| 单进程、单文件锁 | 不能水平扩展，一台挂了没冗余 | 靠客户端多中继冗余绕过 |
| 全内存 + 单日志 | 百万级队列不合适 | P1 换 SQLite / 分片 |
| 无鉴权 | 任何人知道队列 ID 都能往里投 | 这是设计（无标识），靠密文和 OTK 一次性保护 |
| ~~无速率限制~~ | ~~单个连接可以疯狂 put~~ | ✅ 已加：每连接 120 条/分钟，`--rate` 可调 |
| 日志写入在主线程锁内 | 高并发时会有抖动 | P1 改独立写线程 |

> 速率限制已实现（每连接 120 条/分钟）。但它是**单连接维度**的：
> 换连接就重置。真正的抗滥用还需要按 IP / 按队列维度的限制，排到 P1。

## 10. 可选：把中继公布到 Mainline DHT（客户端免手输）

开了这个开关，中继会周期性把自己注册到 BitTorrent 的 Mainline DHT，
客户端就能"自动发现中继"而不用让人手抄地址。

```bash
relay serve --addr 127.0.0.1:8080 --data /var/lib/veilwire \
            --dht-announce 443        # 对外实际端口（反代后的那个）
```

| 参数 | 说明 |
|---|---|
| `--dht-announce [端口]` | 开启公布；不跟端口就用 `--addr` 里的端口。**反代场景必须显式给对外端口** |
| `--dht-interval 600` | 重新公布间隔，默认 600 秒（BEP5 记录会过期，必须定期重播） |

**它做什么**：用 `find_node` 爬到离服务键最近的一批节点，再对它们 `announce_peer`。
同时公布两个键——`veilwire-relays-v1`（WS 端口）和 `veilwire-turn-v1`（TURN 端口，若开了 TURN）。

**必须知道的代价**：

1. **地址变成公开可枚举**。任何人 `get_peers` 就能拿到全部中继清单。
   这是"可自动发现"的必然代价——**只能靠中继数量足够多来抗封**，单点被墙不影响整体。
2. **IP 由 DHT 按来源判定，不能伪造**。所以中继必须从"对外服务的那个 IP"发出公布，
   否则公布出去的是错地址（这也是它防陷害的机制）。
3. **记录会过期**。断了公布，几十分钟后就从 DHT 消失。看日志里
   `[dht] 已公布：WS 端口 ... 成功 N 个节点`，N 长期为 0 就说明网络出问题了。
4. 不想公开就**别开**，默认关闭。手输地址、邀请码里带中继这两条路始终可用。

**验证是否公布成功**：日志出现 `成功 N 个节点（候选 M）` 即成功；
节点表缓存在 `<data>/dht-nodes.json`，下次启动直接复用，绕开被污染的 bootstrap 域名。

### TURN 凭据怎么给客户端（0.15.0 起）

开了 `--turn` 之后，客户端不用再手填账号：连上 WS 时会向中继要一组**临时凭据**。

```
客户端 → {"t":"get_turn"}
中继   → {"t":"turn_creds","url":"turn:<公网IP>:3478","user":"eph-xxxxxxxx","pass":"…","ttl":3600}
```

- 每次请求现签发，`eph-` 前缀便于在日志里区分；到期自动作废，无需吊销
- 客户端缓存在本地（`turn.json`），剩余不足 5 分钟才会重新索取
- 没开 TURN 的中继会回 `no_turn`，客户端自动回退到用户手填的配置

**你要做的**：确认 `--turn-external-ip` 填的是客户端能连到的公网 IP（不是内网地址），
因为它会被原样下发给客户端。日志里出现

```
[turn] 客户端可通过 WS 索取临时凭据，对外地址 turn:203.0.113.10:3478（TTL 1 小时）
```

就说明配置生效了。原来的 `--turn-user/--turn-pass` 仍然有效并优先匹配，
方便你自己留一个固定账号排查问题。
